This page shows how a CI job can exchange its GitHub OIDC token for a theAuth access token, so a deploy or a bot runs as a known identity with a short-lived token and no stored client secret.

<Warning>
  The GitHub Actions helper exists only in the Go library. The TypeScript package has no GitHub-specific helper, and its generic `jwtBearer` grant does not accept a raw GitHub OIDC token. The steps below are the Go flow. The full Go write-up is in [`go/docs/github-actions-oidc.md`](https://github.com/glincker/theauth/blob/main/go/docs/github-actions-oidc.md) in the repository.
</Warning>

## 1. Ask

The job asks GitHub for an OIDC token for a specific audience. The workflow needs `id-token: write`. GitHub then signs a token whose claims name the repository, branch, environment and workflow that ran.

```yaml
name: deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write   # lets the job request an OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Get a GitHub OIDC token
        run: |
          AUD="https://auth.example.com/gh"
          GH_TOKEN=$(curl -sS \
            -H "Authorization: Bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=$AUD" | jq -r .value)
          echo "::add-mask::$GH_TOKEN"
          echo "GH_TOKEN=$GH_TOKEN" >> "$GITHUB_ENV"
```

The job then posts that token to the theAuth token endpoint with the RFC 7523 `jwt-bearer` grant:

```bash
ACCESS=$(curl -sS https://auth.example.com/oauth/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer \
  --data-urlencode "assertion=$GH_TOKEN" \
  -d resource=https://api.example.com/mcp \
  -d scope=api.read | jq -r .access_token)
echo "::add-mask::$ACCESS"
echo "ACCESS_TOKEN=$ACCESS" >> "$GITHUB_ENV"
```

Add `client_id=<agent client id>` to the exchange if the token should act as an agent. The agent's policy and rate limit then apply to the token.

## 2. Find the rule

The server decides which workflows may log in. Build the issuer with `GitHubActionsIssuer`, which refuses to build one with no restriction:

```go
iss, err := theauth.GitHubActionsIssuer(theauth.GitHubActionsOptions{
    Repository:    "acme/app",                  // exact owner/name
    Refs:          []string{"refs/heads/main"}, // or one glob: "refs/heads/release/*"
    Environment:   "production",
    Audience:      "https://auth.example.com/gh",
    SubjectMapper: myWorkflowMapper{},          // GitHub's sub is not a ULID
})
if err != nil {
    log.Fatal(err)
}

cfg.AuthorizationServer = &theauth.AuthorizationServerConfig{
    Issuer:    "https://auth.example.com",
    Resources: resources,
    JWTBearer: &theauth.JWTBearerConfig{TrustedJWTIssuers: []theauth.TrustedJWTIssuer{iss}},
}
```

`GitHubActionsIssuer` sets the issuer, the JWKS URL and `RS256` for you. Each of `Repository`, `RepositoryOwner`, `Refs` and `Environment` adds a claim matcher. All matchers must pass. If `Audience` is empty, the required `aud` is your authorization server issuer URL. `SubjectMapper` maps the GitHub `sub` (for example `repo:acme/app:ref:refs/heads/main`) to a local user, because the built-in mapper expects a ULID.

## 3. See the result

A workflow that matches gets an access token. A workflow that fails any matcher gets `invalid_grant`, with the same generic description every time. The response never names the claim that failed, so a caller cannot probe your config.

A denied exchange returns an OAuth error body with `error` set to `invalid_grant`. Test a denial by running the same workflow from a branch other than `main`.

The operator sees the reason in the audit log:

```json
{"action": "jwt_bearer.claims_denied",
 "targetType": "jwt_issuer", "targetId": "https://token.actions.githubusercontent.com",
 "metadata": {"issuer": "...", "failed_claims": ["repository", "ref"], "agent_id": "...", "agent_name": "..."}}
```

`failed_claims` lists claim names only.

## Evidence and limits

- The GitHub issuer constructor, its matchers and the audit event come from the Go docs linked above. The claim names were read from GitHub's live discovery document, as that page says.
- Tests in the Go library sign tokens with a local key and do not call GitHub. The request-token flow in the workflow has not been run against GitHub from the repository, so check it in your own pipeline first.
- GitHub tokens are short lived. Compare the job duration with `AssertionMaxAge` (default 300 seconds) before you rely on long jobs.
- GitHub signs tokens for every repository with the same issuer. Without `Repository` or `RepositoryOwner`, any public repository's workflow could log in. The constructor refuses that setup. If you build the issuer by hand, add the matchers yourself.
- TypeScript: the `jwtBearer` option in `createMcpModule` expects an ID-JAG assertion (`typ: oauth-id-jag+jwt`, a `client_id` claim and `aud` equal to the issuer). A raw GitHub OIDC token does not match that shape, so it is refused. Read [MCP server grants](/mcp-grants#jwt-bearer-and-id-jag-rfc-7523) before you try it.

## FAQ

### Can I use this from TypeScript?

Not with the current package. There is no GitHub helper, and the generic jwt-bearer grant needs ID-JAG assertions. Use the Go library for this flow.

### Does the job need a client secret?

No. The job holds only the GitHub OIDC token for the run, which GitHub issues for that job and expires. Do not store a theAuth client secret in the repository for this flow.

### What if I want the deploy token limited to one environment?

Set `Environment` in `GitHubActionsOptions`. GitHub applies the environment's protection rules, such as required reviewers, before the job starts, so the token is issued only after approval. Limit scopes with the `scope` and `resource` parameters on the exchange.
