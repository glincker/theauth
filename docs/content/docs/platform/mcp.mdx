## What MCP auth is

The Model Context Protocol (MCP) defines how AI clients connect to tool servers. Starting with the 2025-03 revision, MCP servers can require OAuth 2.1 tokens before accepting tool calls. KavachOS implements a complete MCP-compliant authorization server that issues, validates, and manages these tokens. It handles discovery, client registration, authorization codes, PKCE verification, token issuance, refresh rotation, and scope enforcement.

## What KavachOS implements

The MCP module covers these specifications:

| Specification | What it does |
|---|---|
| OAuth 2.1 (draft-ietf-oauth-v2-1-13) | Authorization code grant with mandatory PKCE |
| PKCE S256 only | Plain PKCE is rejected at the authorization endpoint |
| RFC 8414 | Authorization Server Metadata discovery |
| RFC 9728 | Protected Resource Metadata discovery |
| RFC 8707 | Resource Indicators for audience-bound tokens |
| RFC 7591 | Dynamic Client Registration |

## Setup

### Creating the MCP module

The `createMcpModule` function wires up all MCP OAuth endpoints into a single module. You provide storage callbacks (how to persist clients, codes, and tokens) and a user resolution function (how to identify the authenticated user from a request).

```typescript
import { createMcpModule } from 'kavachos/mcp';

const mcp = createMcpModule({
  config: {
    enabled: true,
    issuer: 'https://auth.yourapp.com',
    baseUrl: 'https://auth.yourapp.com/api/kavach',
    signingSecret: process.env.MCP_SIGNING_SECRET, // >= 32 chars
    scopes: ['mcp:read', 'mcp:write', 'mcp:execute'],
    accessTokenTtl: 3600,      // 1 hour (default)
    refreshTokenTtl: 604800,   // 7 days (default)
    codeTtl: 600,              // 10 minutes (default)
    allowedResources: ['https://mcp.yourapp.com'],
    loginPage: '/login',
    consentPage: '/consent',
    preRegisteredClients: [
      {
        clientId: 'my-cli',
        redirectUris: ['http://localhost:3000/callback'],
        clientName: 'My CLI Tool',
      },
    ],
  },
  storeClient: async (client) => { /* persist to your database */ },
  findClient: async (clientId) => { /* look up by ID */ },
  storeAuthorizationCode: async (code) => { /* persist auth code */ },
  consumeAuthorizationCode: async (code) => {
    // Find and delete in one operation (one-time use)
    const found = await db.query.mcpCodes.findFirst({
      where: eq(mcpCodes.code, code),
    });
    if (found) await db.delete(mcpCodes).where(eq(mcpCodes.code, code));
    return found ?? null;
  },
  storeToken: async (token) => { /* persist token record */ },
  findTokenByRefreshToken: async (rt) => { /* look up by refresh token */ },
  revokeToken: async (at) => { /* delete by access token value */ },
  resolveUserId: async (request) => {
    // Return the authenticated user's ID from session/cookie
    const session = await getSession(request);
    return session?.userId ?? null;
  },
});
```

Then pass the module to your framework adapter:

```typescript
import { kavachHono } from '@kavachos/hono';

const app = kavachHono(kavach, { mcp });
```

## Endpoints

Once mounted via a framework adapter, KavachOS serves these endpoints (paths are relative to your adapter base path):

| Endpoint | Method | RFC | Purpose |
|---|---|---|---|
| `/.well-known/oauth-authorization-server` | GET | RFC 8414 | Authorization server metadata |
| `/.well-known/oauth-protected-resource` | GET | RFC 9728 | Protected resource metadata |
| `/mcp/register` | POST | RFC 7591 | Dynamic client registration |
| `/mcp/authorize` | GET | OAuth 2.1 | Authorization endpoint |
| `/mcp/token` | POST | OAuth 2.1 | Token endpoint (code exchange and refresh) |
| `/mcp/revoke` | POST | RFC 7009 | Token revocation |

## OAuth flow

### PKCE authorization code flow

KavachOS enforces PKCE with S256 on every authorization request. Plain PKCE (`code_challenge_method=plain`) is rejected.

<Steps>
  <Step>
    ### Generate a code verifier

    The client generates a cryptographically random string (43 to 128 characters, URL-safe).

    ```typescript
    const array = new Uint8Array(32);
    crypto.getRandomValues(array);
    const codeVerifier = btoa(String.fromCharCode(...array))
      .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
    ```
  </Step>

  <Step>
    ### Compute the S256 code challenge

    ```typescript
    const encoder = new TextEncoder();
    const data = encoder.encode(codeVerifier);
    const digest = await crypto.subtle.digest('SHA-256', data);
    const codeChallenge = btoa(String.fromCharCode(...new Uint8Array(digest)))
      .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
    ```
  </Step>

  <Step>
    ### Redirect to the authorization endpoint

    ```typescript
    const authUrl = new URL('https://auth.yourapp.com/api/kavach/mcp/authorize');
    authUrl.searchParams.set('response_type', 'code');
    authUrl.searchParams.set('client_id', clientId);
    authUrl.searchParams.set('redirect_uri', 'https://myapp.com/callback');
    authUrl.searchParams.set('code_challenge', codeChallenge);
    authUrl.searchParams.set('code_challenge_method', 'S256');
    authUrl.searchParams.set('scope', 'openid mcp:read mcp:execute');
    authUrl.searchParams.set('state', generateRandomState());
    // Optional: bind token to a specific resource (RFC 8707)
    authUrl.searchParams.set('resource', 'https://mcp.yourapp.com');
    ```

    If the user is not authenticated, KavachOS redirects to `loginPage` with a `returnTo` parameter. If `consentPage` is configured, the user is redirected there to approve scopes before a code is issued.
  </Step>

  <Step>
    ### Exchange the authorization code for tokens

    After the user approves, KavachOS redirects back to `redirect_uri` with a `code` parameter. Exchange it at the token endpoint:

    ```typescript
    const response = await fetch('https://auth.yourapp.com/api/kavach/mcp/token', {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: new URLSearchParams({
        grant_type: 'authorization_code',
        code: authorizationCode,
        redirect_uri: 'https://myapp.com/callback',
        client_id: clientId,
        code_verifier: codeVerifier,
      }),
    });

    const tokens = await response.json();
    // tokens.access_token  - JWT (Bearer)
    // tokens.refresh_token - present when offline_access scope was granted
    // tokens.expires_in    - seconds until expiry
    // tokens.scope         - granted scopes (space-separated)
    ```

    The server computes `base64url(sha256(code_verifier))` and compares it to the stored challenge. A mismatch returns HTTP 400 with `invalid_grant`.
  </Step>

  <Step>
    ### Refresh an expired token

    When the access token expires, use the refresh token to get a new pair. Refresh tokens rotate on every use (the old one is revoked).

    ```typescript
    const response = await fetch('https://auth.yourapp.com/api/kavach/mcp/token', {
      method: 'POST',
      headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
      body: new URLSearchParams({
        grant_type: 'refresh_token',
        refresh_token: currentRefreshToken,
        client_id: clientId,
      }),
    });
    ```
  </Step>
</Steps>

## Token format

Access tokens are JWTs signed with HS256 and typed as `at+jwt`. The payload contains:

| Claim | Description |
|---|---|
| `sub` | The authenticated user ID |
| `iss` | The issuer URL from your config |
| `aud` | The resource URI (from the `resource` parameter, or the issuer if omitted) |
| `exp` | Expiry timestamp (Unix seconds) |
| `iat` | Issued-at timestamp |
| `jti` | Unique token identifier (UUID) |
| `scope` | Space-separated granted scopes |
| `client_id` | The OAuth client that requested the token |

Refresh tokens are opaque 48-byte URL-safe base64 strings. They are not JWTs.

## Token validation

### Using `validateToken`

The MCP module exposes `validateToken` for checking tokens programmatically:

```typescript
const result = await mcp.validateToken(token, ['mcp:read']);

if (!result.success) {
  // result.error.code — INVALID_TOKEN, TOKEN_EXPIRED, INSUFFICIENT_SCOPE, etc.
  // result.error.message — human-readable description
  return new Response('Unauthorized', { status: 401 });
}

const session = result.data;
// session.userId    — the authenticated user
// session.clientId  — the OAuth client
// session.scopes    — granted scopes as string[]
// session.resource  — the audience the token is bound to
// session.expiresAt — Date object
// session.tokenId   — the jti claim
```

Validation checks: JWT signature (HS256), issuer match, audience binding, expiry, and required scopes.

### Using `middleware`

The `middleware` function extracts the Bearer token from the `Authorization` header, validates it, and returns a `Result<McpSession>`:

```typescript
const result = await mcp.middleware(request);

if (!result.success) {
  if (result.error.code === 'UNAUTHORIZED') {
    // No token provided — result.error.details has www-authenticate header
  }
  return new Response(JSON.stringify(result.error), { status: 401 });
}

const session = result.data;
```

### Using `requireScopes`

For endpoints that need specific scopes, `requireScopes` handles the three-branch decision:

1. No token or invalid token: returns a 401 response
2. Valid token but missing scopes: returns a 403 with a step-up challenge
3. Valid token with all scopes: returns the session

```typescript
const check = await mcp.requireScopes(request, ['mcp:write']);

if (!check.authorized) {
  // check.response is a ready-to-send 401 or 403 Response
  return check.response;
}

// check.session is the validated McpSession
const { userId, scopes } = check.session;
```

The 403 response includes a `WWW-Authenticate` header with `error="insufficient_scope"` and an `upgrade_url` the client can use to re-authorize with the needed scopes.

## Dynamic client registration

Clients can register themselves at the `/mcp/register` endpoint per RFC 7591:

```typescript
const response = await fetch('https://auth.yourapp.com/api/kavach/mcp/register', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    redirect_uris: ['https://myapp.com/callback'],
    client_name: 'My MCP Client',
    token_endpoint_auth_method: 'none', // public client
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  }),
});

const client = await response.json();
// client.client_id     — generated UUID
// client.client_secret — present for confidential clients
// client.redirect_uris — echoed back
```

<Callout type="info">
  Public clients (token_endpoint_auth_method: "none") do not receive a client_secret. Confidential clients receive one and must present it at the token endpoint via HTTP Basic auth or body parameters.
</Callout>

You can also pre-register clients in your `McpConfig.preRegisteredClients` array so they exist at startup without a registration call.

## Consent flow

When `consentPage` is set in your config, the authorization endpoint does not issue codes directly. Instead it redirects to your consent page with query parameters containing the authorization details. After the user approves, call `approveConsent`:

```typescript
const result = await mcp.approveConsent({
  userId: authenticatedUserId,
  clientId: params.client_id,
  scope: params.scope,
  state: params.state,
  redirectUri: params.redirect_uri,
  codeChallenge: params.code_challenge,
  codeChallengeMethod: 'S256',
  resource: params.resource,
});

if (result.success) {
  // Redirect the user to result.data.redirectUri
  // (the client's redirect_uri with the authorization code)
}
```
