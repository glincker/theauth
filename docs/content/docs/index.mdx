## What KavachOS is

KavachOS is a TypeScript auth SDK that treats AI agents as first-class identities. You create agents, assign them scoped permissions, and call `authorize()` before every sensitive operation. Each agent gets an opaque bearer token (`kv_...`), each authorization decision is logged with a unique audit ID, and agents can delegate subsets of their permissions to other agents with depth limits and expiry. The core package has zero framework dependencies. It works with any runtime that supports Web API `Request`/`Response`.

<Callout type="info">
KavachOS does not replace your human auth provider. It runs alongside Clerk, Auth.js, better-auth, or whatever you already use. You bring user IDs from your existing system. KavachOS handles everything after that: agent creation, permission enforcement, delegation, and audit.
</Callout>

## The problem

81% of enterprises are deploying AI agents in production, but only 14% have security approval for those deployments. 45% of teams use shared API keys to authenticate agents, with no per-agent identity, no scoped permissions, and no audit trail.

Three things break without agent-specific auth:

- **No identity.** When an agent calls an MCP server or external API, there is no way to say "this request came from agent X, owned by user Y, operating under delegation Z." Shared API keys make every agent indistinguishable.
- **No least privilege.** Granting an agent broad access to complete a task, then hoping it stays in bounds, is not a security model. Permissions need to be declared before the agent runs and enforced on every call.
- **No accountability.** If an agent causes an incident (pushes to the wrong branch, deletes a production record, overspends a token budget), you need a tamper-evident log of what it did and why it was allowed to do it.

## What it includes

- **Agent identity lifecycle.** Create, scope, rotate, expire, and revoke agent tokens.
- **Permission engine.** Resource-based access control with colon-separated hierarchies (`mcp:github:repos`), wildcard matching (`mcp:github:*`), and constraints (rate limits, time windows, IP allowlists, human-in-the-loop gates).
- **Agent-to-agent delegation.** An orchestrator delegates a strict subset of its permissions to a sub-agent, with depth limits and expiry. The full chain is auditable.
- **Immutable audit log.** Every `authorize()` call writes a log entry with the decision, the resource, the agent, and a unique `auditId`. Export as JSON or CSV.
- **Token-based auth.** `authorizeByToken()` validates an incoming bearer token and checks permissions in one call. No JWTs, no network round-trips.
- **MCP OAuth 2.1 server.** Spec-compliant authorization server with PKCE (S256), Protected Resource Metadata (RFC 9728), Resource Indicators (RFC 8707), and Dynamic Client Registration (RFC 7591).
- **Framework adapters.** Drop-in middleware for Hono, Express, Next.js, Fastify, Nuxt, SvelteKit, and Astro.
- **Multi-database.** SQLite for development, Postgres or MySQL in production. All through Drizzle ORM with automatic table creation on startup.
- **Compliance reports.** Generate framework-specific reports for EU AI Act, NIST AI RMF, SOC 2, and ISO 42001.
- **Anomaly detection.** Scan audit logs for unusual patterns: high call frequency, elevated denial rates, off-hours access, and privilege escalation attempts.

```
┌─────────────────────────────────────────────────┐
│  Your application                               │
│                                                 │
│  ┌──────────────┐      ┌──────────────────────┐ │
│  │ Human auth   │      │ KavachOS             │ │
│  │ (Clerk,      │─────>│                      │ │
│  │  Auth.js,    │ user │  agent.create()      │ │
│  │  better-auth)│  ID  │  authorize()         │ │
│  └──────────────┘      │  authorizeByToken()  │ │
│                        │  delegate()          │ │
│                        │  audit.query()       │ │
│                        └──────────┬───────────┘ │
│                                   │             │
│                          allowed / denied       │
│                                   │             │
│                        ┌──────────▼───────────┐ │
│                        │ MCP servers, APIs,   │ │
│                        │ tools, databases     │ │
│                        └──────────────────────┘ │
└─────────────────────────────────────────────────┘
```

Your human auth provider authenticates the user. KavachOS takes the user ID and manages everything about their agents. When an agent wants to do something, your app calls `authorize()` or `authorizeByToken()`, and KavachOS returns `{ allowed, reason, auditId }`.

## Comparison

|  | KavachOS | better-auth (agents plugin) | Roll your own |
|---|---|---|---|
| Agent-first data model | Yes. `AgentIdentity` is the primary entity. | No. Agents are a plugin on top of human auth. | Depends on your design. |
| Wildcard permission matching | Yes. `mcp:github:*` matches `mcp:github:repos`. | No. | You build it. |
| Delegation chains | Yes. Depth limits, expiry, subset enforcement. | No. | Rarely implemented. |
| Constraint types | Rate limits, time windows, IP allowlists, human-in-the-loop. | None. | You build each one. |
| MCP OAuth 2.1 | Yes. PKCE, RFC 9728, RFC 8707, RFC 7591. | No. | Months of spec work. |
| Immutable audit log | Yes. Every decision, exportable as CSV/JSON. | Partial. | You build it. |
| Token rotation | Yes. Atomic, instant invalidation of old token. | No. | You build it. |
| Database support | SQLite, Postgres, MySQL via Drizzle. | SQLite, Postgres, MySQL via Drizzle. | Whatever you wire up. |
| Framework adapters | 7 frameworks. | Many frameworks. | You build each one. |

## What KavachOS is not

KavachOS does not handle login flows, session cookies, OAuth social providers, email verification, or password resets. Those belong in your human auth layer (Clerk, Auth.js, better-auth, or similar). If you need human auth and agent auth in one package, KavachOS is not that. It starts where human auth ends: at the point where an authenticated user creates an agent and hands it a set of capabilities.

KavachOS is also not a gateway or proxy. It does not sit between your agent and external services in the network path. It is a library your application calls to make authorization decisions. Your application is responsible for enforcing those decisions.
