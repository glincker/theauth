The `@glinr/theauth-mcp` server starts read-only. Add `--allow-writes` and it also offers four write tools, each gated by an approval request.

## Read tools

These are always registered: `list_agents`, `get_agent`, `list_delegations`, `list_sessions`, `query_audit`, `check_permission`, `inspect_token`, `doctor` and `get_approval_status`. Tokens and secret-looking fields are redacted.

## Write tools

Registered only when you pass `--allow-writes` (or set `THEAUTH_ALLOW_WRITES=1`):

| Tool | Effect |
| --- | --- |
| `revoke_agent` | Revoke an agent identity |
| `revoke_delegation` | Revoke a delegation chain |
| `rotate_key` | Rotate an agent credential (the new token is not shown to the client) |
| `disable_user` | Disable a user and end its sessions |

```json
{
  "mcpServers": {
    "theauth-admin": {
      "command": "npx",
      "args": ["-y", "@glinr/theauth-mcp", "--allow-writes"],
      "env": {
        "THEAUTH_API_URL": "https://auth.example.com/api",
        "THEAUTH_API_KEY": "...",
        "THEAUTH_MCP_ACTOR": "ops-bot@example.com"
      }
    }
  }
}
```

## How a write is approved

Writes use the same [approval flow](/approval) as the rest of theAuth. No write runs on the first call.

1. The client calls the tool with the target `id`. The server records the request in the audit log, opens an approval request (action such as `admin:revoke_agent`, resource such as `agent:abc`) and returns `{ "status": "pending", "approvalId": "..." }`.
2. A human approves or denies it through your normal approval channel.
3. The client polls `get_approval_status`, or calls the same tool again with `approvalId`.
4. If the request is approved and unexpired, the server spends it and then runs the change. A denied, expired, already used or mismatched approval does nothing.

An approval is single use and tied to one action and one resource, so approving one revoke cannot authorize another.

## Audit

With `THEAUTH_MCP_ACTOR` set (default `theauth-mcp`), every tool call, read or write, is written to the audit log as `admin_mcp.<tool>` with that actor. Writes record each step: requested, pending, executed, denied or failed. If the audit write for a new request fails, the request is not opened.

## Deployment routes

Core ships these routes as an opt-in plugin, `adminApi`. It is off unless `enabled` is exactly `true`; when off, none of the routes exist and each answers 404.

```ts
import { adminApi, createTheAuth } from "@glinr/theauth";

const theauth = await createTheAuth({
  // ...
  plugins: [
    adminApi({
      enabled: true,
      adminUserIds: ["user_ops"],
      systemAgentId: "agent_admin_mcp",
      rateLimit: { max: 60, window: 60 },
    }),
  ],
});
```

| Route | Backed by |
| --- | --- |
| `GET /delegations` | delegation chains, filtered by `agentId` and `status` |
| `DELETE /delegations/{id}` | `revokeDelegation` (cascades to child chains) |
| `GET /sessions` | session list, each row a one-way `ref`, never the session id or a token |
| `POST /users/{id}/disable` | admin `banUser` (ends sessions, revokes agent tokens) |
| `POST /approvals` | `approval.request` |
| `GET /approvals/{id}` | `approval.get` |
| `POST /approvals/{id}/consume` | `consumeApproval` (one conditional update, so a replay or a race is refused with 409) |
| `POST /audit/events` | `recordAuditEvent`, with secret-looking params redacted |

Rules the routes enforce:

- Every call needs an `Authorization: Bearer` credential that resolves to a user in `adminUserIds`. Missing or bad credentials get 401, any other user gets 403, and an empty `adminUserIds` refuses everyone. Cookie-only requests are refused.
- `systemAgentId` must be an existing agent. Approvals and audit rows reference an agent, so the `agentId` and `userId` the MCP server sends are labels and are ignored: the approval is owned by the calling admin and bound to that agent.
- Approval actions must look like `admin:<name>`. Only the admin who opened an approval can consume it, and approving it still happens through your normal approval channel, never through these routes.
- An admin cannot disable itself or another configured admin (unless `allowDisablingAdmins` is set).
- Requests are rate limited per admin user, and ids, enums and body sizes are validated.
