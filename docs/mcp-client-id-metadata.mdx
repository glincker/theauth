A client ID metadata document lets an MCP client identify itself with a URL instead of a pre-registered ID or a dynamic registration call. The client's `client_id` is an `https://` URL that points at a JSON document. theAuth fetches that document when the client first asks for authorization and reads the client's settings from it.

This page covers how that works, how to turn it on, and what your application has to do to use it safely.

## How it works

The `client_id` is an `https` URL with a path, for example `https://app.example.com/oauth/client.json`. It has no query, no fragment, no credentials and no port.

When an authorization request names a client ID that is not already stored, theAuth fetches the URL. The response must be a `200` JSON document, and the document must name itself: its `client_id` field must equal the URL it was fetched from. A document that names a different URL, or that leaves the field out, is rejected.

The document can set the client's redirect URIs, whether the client is public or uses `private_key_jwt`, the grant types and scopes it may request, and display fields. It cannot set a shared secret, and it cannot name an agent. The rules for each field are listed in the document validation section of the design, and any failed rule rejects the whole document.

After a successful fetch, theAuth stores the client and reuses the stored copy until the cache expires. See [Caching and refresh](#caching-and-refresh).

## Enabling it

Turn the feature on in the MCP module config. `consentPage` is required. Without it, `createMcpModule` throws at startup, because any host can publish a client document, so every authorization has to be approved by a user.

```ts
import { createMcpModule } from "@glinr/theauth/mcp";

const mcp = createMcpModule({
  config: {
    // ...issuer, baseUrl, signingSecret, resource
    consentPage: "https://app.example.com/consent",
    clientIdMetadataDocuments: {
      enabled: true,
      resolver: "auto",
      // Optional. Exact hosts or "*.example.com" (subdomains only).
      // When set, nothing outside this list is fetched.
      allowedHosts: ["*.example.com"],
    },
  },
  // ...your storage callbacks
});
```

Choose `resolver` by runtime:

| Runtime | Value | Notes |
| --- | --- | --- |
| Node | `"auto"` | Uses `node:dns` to check the addresses a name resolves to. |
| Bun | `"auto"` | Same as Node. |
| Deno | `"auto"` | Same as Node. |
| Cloudflare Workers | `createDohResolver()` | Resolves names over DNS over HTTPS, because `node:dns` is not available. |
| Cloudflare Workers | `"none"` | Checks host names only, with no address check. Pair it with `allowedHosts`. |

On a runtime without `node:dns`, `"auto"` fails every fetch closed, so set the resolver explicitly. The one exception is a configured `allowedHosts` list: the hosts are then vetted by name, fetches go ahead, and theAuth logs a warning once through the logger (`ctx.logger`, the observability logger) that no address check is running.

## Turning off dynamic registration

Clients that use a metadata document do not need dynamic registration. If you only serve metadata document clients and pre-registered clients, turn registration off:

```ts
registration: { enabled: false }
```

With this set, `POST /mcp/register` answers 404, `registration_endpoint` is left out of the metadata document, and `registerClient` returns `REGISTRATION_DISABLED`. Clients that were registered earlier keep working.

## Building the consent screen

theAuth does not render the consent screen. Your consent page does, and it gets the facts from `mcp.describeClient(clientId, redirectUri?, { firstUse? })`. Without `redirectUri` it describes the client's first registered redirect URI; a URI the client did not register is an error, and so is a blocked, disabled or unknown client. The result is a `Result`, and its data includes these fields:

- `verifiedHost`: the host name of the `client_id`. Show this as the headline, for example "app.example.com wants access".
- `clientName`: the name the client wrote in its document. Show it under the host with the wording "calls itself ...". Never show it alone, and never use it to decide who the client is.
- `logoUri`: the logo the client wrote. The browser loads it, and theAuth does not fetch it.
- `redirectUri` and `redirectHost`: where the approval sends the user. Always show the redirect host.
- `warnings`: a list of codes. Render every one of them.

The warning codes:

| Code | Meaning | What to show |
| --- | --- | --- |
| `redirect_host_differs` | The redirect host is not the client host or a subdomain of it. | A visible caution that approval sends the user to a different site. |
| `localhost_redirect` | The redirect URI is on loopback. Any program on the user's machine can listen there and receive the code. | A visible caution that a local program may be the one asking. |
| `idn_host` | The host contains an `xn--` label. | The name in its ASCII form, and a note that it may look like another name. |
| `name_mentions_other_host` | `clientName` contains a domain name that is not the client host. | A note that the name points at another site. |
| `client_uri_host_differs` | The client's home page is on a different host. | A note with both hosts. |
| `http_redirect` | The redirect URI uses plain http. | A caution that the code travels unencrypted. |
| `bound_to_agent` | An admin bound this client to an agent. | Say that approving lets the client act as that agent. |
| `recently_changed` | The stored document was re-read and updated in the last 24 hours. | A note that the client's settings changed lately. |
| `first_use` | The user has not approved this client before. Your app sets this flag by passing `{ firstUse: true }`. | Extra text on the first approval. |

Show the host first. The client's own name, logo and description are the client author's words, and the author can write anything in them.

## Binding a client to an agent

A client can be bound to an agent so its tokens act as that agent. Only an admin can do this, through the module API:

```ts
await mcp.clients.bindAgent(clientId, agentId);
```

`bindAgent` fetches and stores a client that was never used before it writes the binding, and it throws when the document cannot be fetched, is invalid or is blocked. The document cannot name an agent. A document with an `agent_id` field or a `theauth_*` field is rejected.

After a client is bound, its document can still change. If its `redirect_uris` or `token_endpoint_auth_method` change, the default `onBoundClientChange: "disable"` turns the client off with the reason `cimd_changed_while_bound`. An admin turns it back on with `mcp.cimd.enable(clientId)`. Changes to the keys (`jwks` or `jwks_uri`) do not disable the client. The purpose of this rule is that a takeover of the client's domain does not silently keep the agent's identity.

## Blocking a client

Block a single client by its URL, or every client on a host:

```ts
await mcp.cimd.block({ kind: "url", value: "https://app.example.com/oauth/client.json", reason: "abuse report" });
await mcp.cimd.block({ kind: "host", value: "example.net", reason: "domain sold" });
```

A `host` block also covers subdomains of that host. Blocking a URL does three things: it stops new authorizations, it deletes the client's stored tokens so refresh stops, and it marks the stored client as disabled (reason `blocked`). A host block is checked on every authorize and token call, so clients on that host stop working at once, but their stored rows are not rewritten. Unblocking does not turn a disabled client back on: run `mcp.cimd.enable(clientId)` for that. Remove a block with `mcp.cimd.unblock(id)`, and list blocks with `mcp.cimd.listBlocks()`.

Blocks are stored in the `theauth_mcp_client_blocks` table on database stores. The in-memory store keeps them only for the life of the process.

## Caching and refresh

The cache lifetime comes from the `Cache-Control: max-age` header on the document:

- A `max-age` value is used, clamped to between 60 seconds and 24 hours.
- `no-store`, `no-cache` and `max-age=0` give the 60 second minimum.
- A response without `max-age` gets the default of 1 hour.
- Failed fetches and invalid documents are never stored. A failed URL is retried after 30 seconds at most, so an unreachable host does not get a request on every authorization.

The expiry is stored with the client, so every instance agrees on when to fetch again. When the cache expires, the next authorization or token refresh fetches the document again. If the document has been deleted or no longer names itself correctly, the fetch fails and refresh stops working for that client. Deleting the document is the way a client owner revokes it.

To fetch right away, for example after you change a document, run `mcp.cimd.refresh(clientId)`. It ignores the stored expiry and the retry delay.

A few limits keep anonymous traffic from costing you anything. An unauthenticated `/authorize` request for a metadata document client is answered with a login redirect and neither fetches nor stores anything; the document is fetched once the user is logged in. Fetches are rate limited per registrable domain (`maxFetchesPerHostPerMinute`, default 30). When the store can report it, the number of stored clients nobody has consented to is capped (`maxUnconsentedClients`, default 1000) and stale ones are swept (`unconsentedRetentionSeconds`, default one day). DNS lookups, the JWKS cache (256 entries, 20 keys, 16 KB each) and the failed-fetch memory are all bounded. `onEvent` runs in a microtask and its errors, including a rejected promise from an async hook, are swallowed.

Setting `enabled: false` is a kill switch: stored metadata document clients stop resolving too, so their refresh tokens stop working.

The cache limits can be set with `minCacheSeconds`, `maxCacheSeconds`, `defaultCacheSeconds` and `negativeCacheSeconds`. Their defaults are in the design.

## What is and is not protected

**What theAuth checks.** A client_id must be a canonical https URL on port 443 with a path, no query, no fragment and no credentials. Before fetching, theAuth refuses IP addresses, single label names, local and internal suffixes, and wildcard DNS services such as nip.io and sslip.io. With a resolver it also refuses names that resolve to loopback, private, link-local, carrier-grade NAT, unique-local or cloud metadata addresses. It never follows redirects, reads at most 5 KB, requires a 200 JSON response, gives up after 5 seconds, and fails closed. The document must repeat its own URL as client_id, cannot use shared secrets, and cannot name an agent. Redirect URIs are matched exactly.

**What theAuth cannot check.** It checks a hostname and then lets the runtime's fetch connect, and the runtime resolves the name again. A DNS server built to answer differently each time (DNS rebinding) can make that second lookup point at a private address. This is true on every runtime. With `resolver: "none"` there is no address check at all, only the name rules. DNS over HTTPS answers from public DNS, which can differ from what a server inside your network sees.

**What to do about it.** If you know your clients, set `allowedHosts`: that is the only setting that fully closes the gap. It also covers a document's `jwks_uri`, which must be on an allowed host. Otherwise block private address ranges for outbound traffic from the auth server at the network level. On Cloudflare Workers outbound requests leave from Cloudflare's network, not yours, so a rebinding attack cannot reach your private network from there.

**About names and logos.** client_name and logo_uri are whatever the client's author wrote. Show the client_id hostname as the identity. A redirect URI on localhost means any program on the user's machine can complete the flow as that client, so show the warning theAuth gives you.

**Revocation.** Blocking a client stops new authorizations and refresh tokens at once. A host block also deletes the token rows of that host's stored clients (so unblocking does not bring old refresh tokens back) when the store can list them. Access tokens it already holds stay valid until they expire unless you configure `jtiDenylist`. A URL block must be the canonical client_id.
