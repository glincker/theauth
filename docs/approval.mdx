## What approval flows solve

Some agent actions are too sensitive to run without a human saying yes first. File deletions, financial transfers, permission escalations, these benefit from a checkpoint before execution.

theAuth supports this with a permission constraint called `requireApproval`. When the permission engine sees it, authorization is denied with the reason `"This action requires human approval before execution"`. Your application catches that signal, creates an approval request, notifies a human, and retries the action after a response comes back.

The flow is async. The agent does not block waiting. The human can respond minutes or hours later, within the request's TTL.

<Warning>
  An approval only unlocks an action when the call carries its id. A permission with `requireApproval: true` is still denied every time unless you pass `approvalId` to `authorize()` or `policy.evaluate()`. `approve()`, `deny()` and `decide()` refuse a request past its `expiresAt` and mark it `expired`. `cleanup()` marks every overdue pending request as `expired`.
</Warning>

<Info>
  theAuth creates the approval request and persists it. Delivering the notification to the human, email, Slack, push notification, is your application's job. Use `webhookUrl` or `onApprovalNeeded` to hook into your existing notification stack.
</Info>

## How the flow works

<Steps>
  <Step>
    **Agent triggers approval**

    The agent calls an action protected by `requireApproval: true`. Authorization is denied. Your application detects the denial reason and calls `theauth.approval.request()`.
  </Step>
  <Step>
    **Human gets notified**

    When you call `theauth.approval.request()`, theAuth persists the request and fires your `webhookUrl` or `onApprovalNeeded` handler with the request details. Your app sends an email, opens a Slack DM, or surfaces a notification in your dashboard.
  </Step>
  <Step>
    **Human approves or denies**

    The human clicks a button in your UI. Your UI calls your backend, which calls `theauth.approval.approve(requestId)` or `theauth.approval.deny(requestId)`.
  </Step>
  <Step>
    **Agent retries**

    Check the decision with `theauth.approval.get(requestId)`. Once the status is `approved`, call `authorize()` or `policy.evaluate()` again with `approvalId: requestId`. theAuth verifies and spends the approval and allows the call, then your application carries out the action. Pass the request ID back to the agent so it can poll or be woken up when a decision arrives.
  </Step>
</Steps>

## Spending an approval

Pass `approvalId` on the request:

```typescript
const result = await theauth.authorize(agentId, {
  action: "execute",
  resource: "mcp:payments:refund",
  approvalId: request.id,
});

const decision = await theauth.policy.evaluate({
  subject: { agentId, ownerId },
  action: "execute",
  resource: "mcp:payments:refund",
  approvalId: request.id,
});
```

When the matched permission requires approval (or `policy.evaluate` would escalate for a risk tier that requires `approval`), theAuth checks that the request exists, is `approved`, belongs to this agent, has exactly this action and resource, has not expired and has not been used. It then marks the request consumed and allows the call. An approval is single use: the check and the consume are one conditional update (`consumed_at IS NULL`), so when two calls race with the same `approvalId` exactly one is allowed. Other constraints on the permission, such as `timeWindow` and `ipAllowlist`, still apply, and a call that fails them does not use up the approval. A tier that requires `step_up` is not satisfied by an approval.

If the approval cannot be spent, the call is denied with one of these reasons:

| `reason` | `code` | Meaning |
| --- | --- | --- |
| `APPROVAL_NOT_FOUND` | `approval_not_found` | No request has this id. |
| `APPROVAL_PENDING` | `approval_pending` | Nobody has answered yet. |
| `APPROVAL_DENIED` | `approval_denied` | A human denied the request. |
| `APPROVAL_MISMATCH` | `approval_mismatch` | The request is for another agent, action or resource. |
| `APPROVAL_ARGUMENTS_MISMATCH` | `approval_arguments_mismatch` | The call's arguments differ from the ones the human approved. |
| `APPROVAL_EXPIRED` | `approval_expired` | The request passed its `expiresAt`, answered or not. |
| `APPROVAL_ALREADY_USED` | `approval_already_used` | The request was already spent. |

The approval is bound to a hash of the action, resource and arguments. Reserved keys such as `approvalId` are stripped from the arguments before hashing, and a request stored without arguments only covers a call without arguments. The canonical form is the one theauth-go hashes, so the same request has the same hash in both libraries for JSON shaped arguments (object keys sorted by UTF-8 bytes, Go's string escaping including `<`, `>` and `&`, float64 number text). An argument that cannot be hashed, such as `NaN`, `Infinity` or a reference cycle, never matches an approval. An integer beyond 2^53 only matches across languages when the TypeScript side passes a `bigint`, because a JavaScript number has already lost its low digits. A successful spend returns `allowed: true` with code `approval_consumed`. The generic `approval_invalid` code is no longer returned.

The allow is audited with `approver_id` set to the request's `respondedBy` and the approval id in the row's `parameters.approvalId`. Upgrading adds a nullable `consumed_at` column to `theauth_approval_requests` automatically.

## Requesting and deciding

```typescript
const req = await theauth.approval.request({
  agentId,
  userId: ownerId,
  action: "execute",
  resource: "mcp:payments:refund",
  arguments: { amount: 10 },
});

// The owner's inbox: pending and not yet expired.
const inbox = await theauth.approval.listPending(ownerId);

await theauth.approval.decide(req.id, { decision: "approve", decidedBy: ownerId });
// or: theauth.approval.approve(id, by), theauth.approval.deny(id, by)
```

Every step writes an audit row (`approval.request`, `approval.approve`, `approval.deny`, `approval.expire`). When `observability.onDecision` is set, each step also emits a decision event with `source: "approval"`:

| Step | `decision` | `code` |
| --- | --- | --- |
| request | `escalate` | `approval_pending` |
| approve | `allow` | `approval_granted` |
| deny | `deny` | `approval_denied` |
| expire | `deny` | `approval_expired` |

Spending the approval in `authorize()` emits the usual event with code `approval_consumed`.

## ApprovalRequest fields

<ParamField path="id" type="string">Unique identifier prefixed apr_.</ParamField>
<ParamField path="agentId" type="string">The agent requesting approval.</ParamField>
<ParamField path="userId" type="string">The user who owns the agent and should receive the notification.</ParamField>
<ParamField path="action" type="string">The action the agent wants to perform.</ParamField>
<ParamField path="resource" type="string">The resource the action targets.</ParamField>
<ParamField path="arguments" type={`Record<string, unknown> | undefined`}>The arguments the agent passed at the time of the call.</ParamField>
<ParamField path="status" type="'pending' | 'approved' | 'denied' | 'expired'">Current state. Only `pending` requests can be approved or denied; `approve()` and `deny()` throw on any other status.</ParamField>
<ParamField path="expiresAt" type="Date">When the request expires if no response is received. Default TTL is 5 minutes (`ttl` is in seconds).</ParamField>
<ParamField path="respondedAt" type="Date | undefined">When the human responded.</ParamField>
<ParamField path="respondedBy" type="string | undefined">Identifier of the person who approved or denied.</ParamField>
<ParamField path="createdAt" type="Date">When the request was created.</ParamField>

## Configuration

Pass approval config to `createTheAuth`:

```typescript
const theauth = await createTheAuth({
  database: { provider: 'sqlite-native', url: 'theauth.db' },
  approval: {
    ttl: 600,                                          // 10-minute window (seconds)
    webhookUrl: 'https://your-app.com/webhooks/approval',
  },
});
```

Or use a custom handler for full control over delivery:

```typescript
const theauth = await createTheAuth({
  database: { provider: 'sqlite-native', url: 'theauth.db' },
  approval: {
    ttl: 300,
    onApprovalNeeded: async (request) => {
      await sendSlackDm(request.userId, {
        text: `Agent ${request.agentId} wants to ${request.action} on ${request.resource}.`,
        approveUrl: `https://your-app.com/approvals/${request.id}/approve`,
        denyUrl: `https://your-app.com/approvals/${request.id}/deny`,
      });
    },
  },
});
```

Both `webhookUrl` and `onApprovalNeeded` fire asynchronously (not awaited) so the `request()` call is not delayed by notification latency. If both are set, both fire.

## The approval.pending webhook

When `webhooks` is configured, a new pending request also sends `approval.pending` to endpoints that subscribe to it. The payload carries `approvalId`, `agentId`, `userId`, `action`, `resource`, `argumentsHash`, `expiresAt` and `createdAt`. It never carries the raw arguments, so fetch them with `approval.get(approvalId)` when your approver needs to see them.

## How webhooks work

When `webhookUrl` is set, theAuth sends a `POST` to that URL with a JSON body:

```json
{
  "event": "approval_needed",
  "request": {
    "id": "apr_...",
    "agentId": "agt_...",
    "userId": "user-123",
    "action": "delete",
    "resource": "file:prod-data/*",
    "arguments": { "path": "/prod/dataset.csv" },
    "status": "pending",
    "expiresAt": "2026-03-21T10:15:00.000Z",
    "createdAt": "2026-03-21T10:10:00.000Z"
  }
}
```

The webhook is a plain `POST` with no signature header and no retries. Delivery failures are non-fatal. The request is already persisted, your app can poll `listPending()` as a fallback.

## Code examples

### Set up a permission that requires approval

```typescript
const agent = await theauth.agent.create({
  ownerId: 'user-123',
  name: 'file-manager',
  type: 'autonomous',
  permissions: [
    {
      resource: 'file:prod-data/*',
      actions: ['read'],
    },
    {
      resource: 'file:prod-data/*',
      actions: ['delete'],
      constraints: { requireApproval: true },
    },
  ],
});
```

### Catch the denial and create a request

```typescript
const result = await theauth.authorize(agent.id, {
  action: 'delete',
  resource: 'file:prod-data/dataset.csv',
  arguments: { path: '/prod/dataset.csv' },
});

if (!result.allowed && result.reason?.includes('requires human approval')) {
  const approvalRequest = await theauth.approval.request({
    agentId: agent.id,
    userId: agent.ownerId,
    action: 'delete',
    resource: 'file:prod-data/dataset.csv',
    arguments: { path: '/prod/dataset.csv' },
  });

  return { pending: true, approvalId: approvalRequest.id };
}
```

### Approve or deny from your UI handler

```typescript
// In your API route handler
app.post('/approvals/:id/approve', async (req, res) => {
  const updated = await theauth.approval.approve(req.params.id, req.user.email);
  res.json({ status: updated.status });
});

app.post('/approvals/:id/deny', async (req, res) => {
  const updated = await theauth.approval.deny(req.params.id, req.user.email);
  res.json({ status: updated.status });
});
```

### List pending requests for a user

```typescript
// All pending approvals across all users
const all = await theauth.approval.listPending();

// Pending approvals for a specific user
const forUser = await theauth.approval.listPending('user-123');

console.log(`${forUser.length} approvals waiting on user-123`);
```

### Expire stale requests

Requests that exceed their TTL are still stored with `status: 'pending'` until you run cleanup. Call this from a cron job:

```typescript
const result = await theauth.approval.cleanup();
console.log(`Expired ${result.expired} stale approval requests`);
```

### Check the status before retrying

```typescript
const request = await theauth.approval.get('apr_...');

if (request?.status === 'approved') {
  // Approved. Call authorize() again with approvalId: request.id. It spends
  // the approval once and allows the call, then you carry out the action.
  await deleteFile('/prod/dataset.csv');
} else if (request?.status === 'denied') {
  console.log('Human denied the request.');
} else if (request?.status === 'expired') {
  console.log('Request expired without a response.');
}
```

## Requiring a fresh passkey or TOTP code

For risky actions you can require that the person approving just proved who they are. Set `approval.requireAcr`, `approval.maxAuthAge` or an `approval.stepUp` callback, or pass `stepUp` to `request()`. The rule is stored on the request and enforced when someone approves it. See [step-up authentication](/step-up-auth).
