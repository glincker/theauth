## Overview

The audit log records what agents do. By default nothing stops someone with database write access from editing or deleting a row afterwards. Turn on the hash chain and every new row stores the hash of the row before it, so an edit, a deletion or a reorder shows up the next time you verify.

It is off by default and additive. Rows written before you enable it are left alone and are reported as unchained.

```ts
import { createTheAuth } from "@glinr/theauth";

const theauth = await createTheAuth({
  database: { provider: "postgres", url: process.env.DATABASE_URL },
  agents: { enabled: true },
  audit: {
    tamperEvident: true,
    // Without a key anyone who can write to the database can recompute the chain.
    hmacKey: process.env.AUDIT_HMAC_KEY,
  },
});
```

## What gets recorded

With `agents.auditAll` on (the default), every decision about a known agent writes one row, allowed or denied. That includes a request from an agent that is revoked or expired. Those rows have `result: "denied"` and a stable `reason` code, so you can filter for them:

| `reason` | Written when |
|---|---|
| `agent_revoked` | `authorize(agentId)` or `authorizeByToken(token)` is called for a revoked agent |
| `agent_expired` | The same calls for an agent whose status is `expired`, or whose `expiresAt` has passed, even if its stored status is still `active` |

The `reason` string on the returned result is unchanged (for example `Agent "deploy-bot" is revoked`). The row stores the short code. The row never stores the token. It stores the action, resource, `arguments`, IP and user agent, like any other row, and it goes through the same writer, so with `tamperEvident` on it joins the agent's chain like any other row.

Policy decisions from `theauth.policy.evaluate()` write a row too, with `result: "escalated"` when the outcome is `escalate`. Delegation and approval events write rows as well (`delegation.create` and `delegation.revoke`, and the approval request and answer, which carries the `approver_id`). Every row names what happened in its `event` column; see [event vocabulary](/audit#event-vocabulary).

Some denials write no row:

- **Unknown agent id** (`authorize("no-such-agent")`). There is no agent to attach a row or a chain to, and the audit table requires a real agent. Writing rows keyed by arbitrary ids would let a caller fill the table with junk.
- **Unknown token** (`authorizeByToken` with a token that matches no agent). Same reason. Nothing identifies an agent.
- **Blocked by a `beforeAuthorize` hook.** The hook runs before any database work by design. Use `onViolation` to log these.
- **`agents.auditAll: false`.** No rows are written for any decision, including these.

When no row is written, `auditId` on the result is an empty string.

A failed audit write on one of these denials does not change the outcome. The call still returns `allowed: false` and does not throw, and `auditId` is empty. This differs from an allow or a permission denial, where a failed audit insert propagates as an error.

A caller holding a revoked token can produce one row per attempt. Use `audit.cleanup({ retentionDays })` and your gateway's rate limiting if that matters for you.

### Fields on each row

Besides the action, resource, arguments and result, a row can carry:

| Field | Holds |
|---|---|
| `event` | What happened (`authorize`, `policy.evaluate`, `delegation.create`, ...). `action` stays the domain verb. Not part of the hash, so adding it never changes an existing chain |
| `subject_id` | The accountable human: the root owner of the delegation chain, else the agent's owner |
| `actor_id` | The agent that acted |
| `policy_version` | The `policy.policyVersion` label active when the decision was made |
| `approver_id` | Who answered, on approval rows and on the decision that spends an approval (its `parameters.approvalId` holds the request id) |
| `delegation_chain` | Agent ids from the root delegator to the actor, when delegated |
| `input_provenance` | Free-form JSON describing where the inputs came from |
| `hash_version` | `2` for rows that hash pseudonyms of the ids (see below), null or `1` for older rows |

`input_provenance` is filled when you supply labels to the tool guard (see [taint guard](/taint-guard)) or pass it to `recordAuditEvent`. The SDK does not infer provenance by itself, so an empty value does not mean the inputs were trusted.

### Write failures

Audit writes from `recordAuditEvent` (policy decisions, delegation, approval and SCIM events) are best effort. They do not throw and do not fail the operation they describe. Each failure is counted: read the total with `getAuditWriteFailures(db)`, or pass `audit.onAuditError` to be called with `{ error, pendingFailures, totalFailures }`. The next successful write is preceded by an `audit.write_failed` row that records how many writes were lost, so a gap in the log is visible.

## How the chain works

There is one chain per agent. Each row gets `chain_seq` (1, 2, 3...), `prev_hash` and `hash`. The hash is SHA-256 over the canonical JSON (sorted keys) of the row fields, the sequence number and `prev_hash`. With `hmacKey` it is HMAC-SHA256 instead.

Why per agent and not per tenant or global: writers for different agents never contend, a replay is exactly one chain, and a single unique index on `(agent_id, chain_seq)` is enough to stop a fork.

Concurrent writers do not need a transaction or a lock. A writer reads the chain head, computes the next hash and inserts. If another writer took that sequence number first, the unique index rejects the insert and the writer re-reads the head and retries. This behaves the same on SQLite, Postgres, MySQL and D1. Writers inside one process also queue per agent, so retries only happen across processes.

Timestamps are hashed at one-second precision, because that is what the SQLite column stores.

### Pseudonymized ids and erasure

Rows with `hash_version` 2 hash keyed pseudonyms of `user_id`, `agent_id`, `subject_id`, `actor_id` and `approver_id` instead of the raw ids, and store the pseudonyms on the row. The key is `audit.hmacKey` when set, otherwise a random secret stored in `theauth_audit_secrets`. GDPR erasure (`deleteUser`) can then blank or replace the raw ids and the row hash still verifies.

Rows written before this format (`hash_version` null or 1) hash the raw ids, so rewriting them would break the hash. For those rows, and for rows deleted outright, erasure writes an `audit.erasure` record naming each affected row with its stored hash. `verifyAuditChain` reports them in an `erased` count instead of as tampering.

A pseudonym is linkable by whoever holds the key, so this is pseudonymization, not anonymization. Destroying the key is not implemented. The erasure path rewrites rows with SQLite-specific statements.

### Migration

`createTables` adds the three nullable columns and the unique index to an existing `theauth_audit_logs` table. The statements are idempotent (Postgres uses `ADD COLUMN IF NOT EXISTS`, SQLite and MySQL tolerate "already exists"). If you run with `skipMigrations: true`, apply this yourself:

```sql
ALTER TABLE theauth_audit_logs ADD COLUMN chain_seq INTEGER;
ALTER TABLE theauth_audit_logs ADD COLUMN prev_hash TEXT;
ALTER TABLE theauth_audit_logs ADD COLUMN hash TEXT;
CREATE UNIQUE INDEX theauth_audit_logs_chain ON theauth_audit_logs (agent_id, chain_seq);
-- MySQL: use (agent_id(191), chain_seq)
```

Without the unique index, concurrent writers can fork a chain.

## Verify

```ts
const result = await theauth.audit.verifyAuditChain({
  from: new Date("2026-10-01"),
  to: new Date("2026-10-31"),
});

if (result.success && !result.data.ok) {
  const b = result.data.firstBreak!;
  console.error(`${b.reason} for agent ${b.agentId} at seq ${b.seq}`, b.rowIds);
}
```

Break reasons: `hash_mismatch` (a row was edited), `seq_gap` (a row was deleted), `prev_hash_mismatch` (rows were reordered or relinked), `missing_hash`, `truncated`, and `pseudonym_mismatch` (a raw id was edited after the row was written). The result also reports `unchained` and `erased` counts. Retention cleanup (`audit.cleanup`) writes an `audit.checkpoint` row recording where the chain was cut, so removing the oldest rows on purpose does not read as a break.

Deleting the newest rows of a chain leaves a shorter chain that still verifies. To catch that, keep a chain head somewhere the database owner cannot edit (an export manifest works) and pass it back:

```ts
await theauth.audit.verifyAuditChain({ expectedHeads: manifest.heads });
```

## Replay an agent

```ts
const replay = await theauth.audit.replayAgent("agent_123", {
  since: new Date("2026-10-01"),
  until: new Date("2026-10-02"),
  userId: "user_456", // optional: only what it did for this user
});

if (replay.success) {
  for (const e of replay.data.events) console.log(e.at.toISOString(), e.kind, e.summary);
  console.log(replay.data.verification.status); // "verified" | "broken" | "unchained"
}
```

The timeline merges audit rows (`action` when allowed, `decision` when denied or rate limited), delegations the agent gave or received, approval requests and answers, and token cost events, ordered by time. Only audit rows are covered by the chain, and each event says whether it is `chained`. The `userId` filter applies to audit rows and approvals.

## Export for compliance

```ts
const exported = await theauth.audit.exportAudit({
  agentId: "agent_123",
  since: new Date("2026-10-01"),
  until: new Date("2026-10-31"),
});

if (exported.success) {
  await writeFile("audit.jsonl", exported.data.jsonl);
  await writeFile("audit.manifest.json", JSON.stringify(exported.data.manifest, null, 2));
}
```

The manifest holds the SHA-256 of the file, the row count, the range, the chain head per agent, whether the chain verified, and an HMAC signature over all of that. It is signed with `audit.hmacKey` (or `signingKey` if you pass one); export fails with `NO_SIGNING_KEY` otherwise. Check an export later without a database:

```ts
import { verifyAuditExport } from "@glinr/theauth";

const check = await verifyAuditExport({ jsonl, manifest }, process.env.AUDIT_HMAC_KEY!);
console.log(check.ok, check.problems);
```

Exports are capped at 100,000 rows; narrow the range for more.

## CLI

```bash
export DATABASE_URL=postgres://...
export THEAUTH_AUDIT_HMAC_KEY=...   # same value as audit.hmacKey, if you set one

theauth audit verify --from 2026-10-01 --json
theauth audit replay --agent agent_123 --since 2026-10-01 --json
```

Both exit 1 when the chain is broken. `--db <url>` overrides `DATABASE_URL`. The commands never write.

## Limits

- Tail truncation is only detectable against a saved head (see above).
- Anyone holding `hmacKey` and database write access can forge a chain. Keep the key outside the database host.
- Retention cleanup and GDPR erasure remove or rewrite rows. Cleanup leaves a checkpoint row and erasure leaves an `audit.erasure` record. Rewriting a row in the middle by other means is flagged.
- A pseudonym is linkable by whoever holds the key (`audit.hmacKey` or the stored secret).
- `input_provenance` comes from labels you supply. The SDK does not infer it.
- Audit writes for policy decisions, delegation, approval and SCIM events are best effort. Failures are counted and followed by an `audit.write_failed` row (with the count and the first and last failure times), but a write that fails is not retried.
