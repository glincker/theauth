## What is a delegation chain

A delegation chain lets one agent grant a subset of its permissions to another. The delegating agent keeps its own permissions unchanged. The receiving agent gains access only to what was explicitly delegated.

This pattern is most useful when an orchestrator spins up sub-agents for specific tasks. Each sub-agent gets only the access it needs, for only as long as it needs it.

<Frame caption="A delegation chain is capped by maxDepth, and revoking a link also revokes the links created downstream of it.">
  <img src="/images/diagrams/delegation-chain.png" alt="Isometric diagram of a human owner, an agent and two sub-agents joined by delegation links. Delegation depth is limited to 3, and revoking a link also revokes the links downstream of it." />
</Frame>

<Info>
The delegating agent must currently hold every permission it is trying to delegate. Attempting to delegate a permission not in the agent's own set throws an `Error` ("Delegated permissions must be a subset of the parent agent's permissions..."). The check runs against the agent's own permissions only, not against permissions it received through other delegations.
</Info>

## Working with delegations

### Creating a delegation

```typescript
const chain = await theauth.delegate({
  fromAgent: orchestrator.id,
  toAgent: subAgent.id,
  permissions: [
    { resource: 'mcp:github:issues', actions: ['read'] },
  ],
  expiresAt: new Date(Date.now() + 3_600_000), // 1 hour
  maxDepth: 2,
});

console.log(chain.id);        // dlg_...
console.log(chain.depth);     // 1
console.log(chain.expiresAt); // Date
```

<ParamField path="fromAgent" type="string">Agent ID granting the permissions. Must hold every permission being delegated, either as its own permission or through a delegation it received.</ParamField>
<ParamField path="toAgent" type="string">Agent ID receiving the permissions.</ParamField>
<ParamField path="permissions" type="Permission[]">Subset of permissions to delegate. Must not exceed what the fromAgent holds (its own permissions plus the active, unexpired delegations it received).</ParamField>
<ParamField path="expiresAt" type="Date">When the delegation expires. After this point, the chain is no longer valid.</ParamField>
<ParamField path="maxDepth" type="number">Highest chain depth this link and any later link below it may reach. The new link's depth (1 for a first hop, parent depth plus 1 for a re-delegation) must be less than or equal to the effective limit, otherwise the call throws. Default is 3. The limit is inherited: a re-delegation is checked against the smaller of its own `maxDepth` and the `maxDepth` of every active delegation the parent received.</ParamField>

### Permission subset enforcement

The permissions you delegate must be a subset of what the `fromAgent` holds. Narrower resources and fewer actions are allowed. Wider resources or new actions are rejected.

Given an orchestrator with:

```typescript
{ resource: 'mcp:github:*', actions: ['read', 'write', 'comment'] }
```

Valid delegations:

```typescript
{ resource: 'mcp:github:issues', actions: ['read'] }           // narrower resource, fewer actions
{ resource: 'mcp:github:*', actions: ['read'] }                // same resource, fewer actions
{ resource: 'mcp:github:repos', actions: ['read', 'comment'] } // narrower resource, same actions
```

Invalid delegations:

```typescript
{ resource: 'mcp:github:*', actions: ['delete'] }  // action not held by parent
{ resource: 'mcp:slack:*', actions: ['read'] }     // resource not held by parent
```

### Constraints carry over

Constraints on the permissions you delegate are stored on the chain and enforced by `authorize()`, `authorizeByToken()` and `policy.evaluate()`. They are narrowed against the permission the parent holds, so a child can only be tighter:

| Constraint | Result |
|---|---|
| `requireApproval` | True if either side sets it |
| `maxCallsPerHour` | The lower of the two values |
| `allowedArgPatterns`, `ipAllowlist` | The patterns or addresses both sides share. If none are shared, the parent's list stays. |
| `timeWindow` | The overlap of two same-day windows. Otherwise the parent's window stays. |

```typescript
await theauth.delegate({
  fromAgent: orchestrator.id,
  toAgent: worker.id,
  permissions: [
    { resource: 'mcp:payments:refund', actions: ['execute'], constraints: { requireApproval: true } },
  ],
  expiresAt: new Date(Date.now() + 15 * 60_000),
  maxDepth: 1,
});
```

### Depth limiting

Each link has a depth: 1 for a delegation from an agent that did not itself receive one, otherwise the deepest active chain into the delegating agent plus 1. On every `delegate()` call the code computes an effective limit, the smallest of the `maxDepth` passed on that call (default 3) and the `maxDepth` stored on every active, unexpired delegation into the delegating agent, and throws if the new link's depth is larger. The effective limit is stored on the new link, so a limit set at the top of a chain holds for every hop below it. A later call can lower it, never raise it.

```typescript
// Orchestrator → Sub (depth 1, maxDepth 2): allowed
await theauth.delegate({
  fromAgent: orchestrator.id,
  toAgent: sub.id,
  permissions: [{ resource: 'mcp:github:issues', actions: ['read'] }],
  expiresAt: new Date(Date.now() + 3_600_000),
  maxDepth: 2,
});

// Sub → SubSub (depth 2, limit min(2, 2) = 2): allowed
await theauth.delegate({
  fromAgent: sub.id,
  toAgent: subSub.id,
  permissions: [{ resource: 'mcp:github:issues', actions: ['read'] }],
  expiresAt: new Date(Date.now() + 1_800_000),
  maxDepth: 2,
});

// Sub → anyone with maxDepth: 1 is rejected: depth 2 exceeds limit 1
// SubSub → anyone, even with maxDepth: 10, is rejected: depth 3 exceeds the inherited limit 2
```

The default `maxDepth` when not specified is `3`.

<Info>
A delegating agent can re-delegate permissions it received. The subset check runs against the agent's own permissions plus the active delegations into it, so `sub` above, created with `permissions: []`, can pass on what it was given, never more. The new link also cannot outlive the delegation it was derived from: its expiry is capped at the earliest expiry among the delegations into the parent, unless the parent's own permissions already cover the request.
</Info>

### Cascading revocation

Revoking a chain marks it revoked and does the same for active chains that start from the receiving agent.

```typescript
await theauth.delegation.revoke(chain.id);
```

If the chain is `orchestrator → sub → subSub`, revoking `orchestrator → sub` also revokes `sub → subSub` immediately. Any agent that relied on the revoked permissions will get `allowed: false` on its next authorization check.

<Warning>
Revocation takes effect on the next `authorize()` call. It does not terminate any in-progress operations.
</Warning>

<Note>
In the TypeScript package, `agent.revoke()` also revokes every active chain where the agent is the source or the target, and the chains downstream of them. It returns their ids as `revokedDelegations` and writes one `agent.cascade.revoked` audit row for the agent. Use `delegation.revoke()` when you want to cut one chain and keep the agent. This `agent.revoke()` cascade is pending in a changeset and is available in the next release after 1.1.2. Before it, revoke the agent's chains with `delegation.revoke()`.
</Note>

<Note>
Tokens minted through MCP token exchange carry their chain in the `act` claim. Set `delegationStore` in the MCP config to have the resource server re-check that chain against live records, so revoking a parent chain rejects tokens issued down it before they expire. See [MCP auth](/mcp).
</Note>

### Effective permissions

To see the full set of permissions an agent has at a given moment, including those received through active chains:

```typescript
const effective = await theauth.delegation.getEffectivePermissions(subAgent.id);
// Returns only the Permission[] received through active, unexpired delegation chains
```

`authorize()` checks the agent's own permissions first and, if they deny, falls back to these delegated permissions. You can call it directly to inspect what an agent has received through delegation.

### Listing chains

```typescript
// All chains originating from the orchestrator (fromAgent === agentId)
const outbound = await theauth.delegation.listChains(orchestrator.id);
```

### DelegationChain type

<ParamField path="id" type="string">Unique chain identifier, prefixed dlg_.</ParamField>
<ParamField path="fromAgent" type="string">Agent ID that created the delegation.</ParamField>
<ParamField path="toAgent" type="string">Agent ID that received the delegation.</ParamField>
<ParamField path="permissions" type="Permission[]">The permissions granted by this chain.</ParamField>
<ParamField path="expiresAt" type="Date">Expiry time for the chain.</ParamField>
<ParamField path="depth" type="number">Current depth of this chain in the delegation tree.</ParamField>
<ParamField path="createdAt" type="Date">When the chain was created.</ParamField>
<ParamField path="rootOwnerId" type="string | undefined">The human who owns the root agent of the chain. If the delegating agent was itself delegated to, the walk continues upward through active, unexpired chains, following the earliest created one when there are several.</ParamField>
<ParamField path="path" type="string[] | undefined">Agent ids from the root delegator down to `toAgent`.</ParamField>

`rootOwnerId` and `path` are returned by `delegate()` (`listChains()` does not include them). `policy.evaluate()` returns the same lineage as `decision.principal`, and each delegation is written to the audit log with the lineage on the row. The audit write is best effort: a failure does not fail the delegation, and it is counted (see [Tamper-evident audit trail](/audit-trail#write-failures)).

## Typical pattern

An orchestrator holds broad permissions, plans a task, and issues short-lived narrow delegations to sub-agents.

<Steps>
  <Step>
    Create the orchestrator with the full permission set it needs.

    ```typescript
    const orchestrator = await theauth.agent.create({
      ownerId: 'user-123',
      name: 'planner',
      type: 'autonomous',
      permissions: [
        { resource: 'mcp:github:*', actions: ['read', 'write', 'comment'] },
        { resource: 'mcp:linear:*', actions: ['read', 'write'] },
      ],
    });
    ```
  </Step>
  <Step>
    Create the sub-agent with no direct permissions.

    ```typescript
    const codeReviewer = await theauth.agent.create({
      ownerId: 'user-123',
      name: 'code-reviewer',
      type: 'delegated',
      permissions: [],
    });
    ```
  </Step>
  <Step>
    Delegate only what the sub-agent needs, with a short expiry and a small `maxDepth` (later hops inherit it, see depth limiting above).

    ```typescript
    await theauth.delegate({
      fromAgent: orchestrator.id,
      toAgent: codeReviewer.id,
      permissions: [
        { resource: 'mcp:github:pulls', actions: ['read', 'comment'] },
      ],
      expiresAt: new Date(Date.now() + 30 * 60_000), // 30 minutes
      maxDepth: 1,
    });
    ```
  </Step>
</Steps>
