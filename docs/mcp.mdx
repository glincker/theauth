## What MCP auth is

The Model Context Protocol defines how AI clients connect to tool servers. The 2025-03 revision added an auth layer: MCP servers can now require OAuth 2.1 tokens before accepting tool calls.

<Frame caption="The MCP client discovers, registers and authorizes with PKCE S256, then the MCP server validates the token.">
  <img src="/images/diagrams/mcp-oauth.png" alt="Isometric diagram of an MCP client discovers, registers with and authorizes against the theAuth authorization server using PKCE S256, receives a token, and the MCP server validates that token." />
</Frame>

theAuth implements the full MCP auth stack:

- OAuth 2.1 with PKCE (S256 code challenge method only)
- Protected Resource Metadata (RFC 9728)
- Authorization Server Metadata (RFC 8414)
- Resource Indicators (RFC 8707)
- Dynamic Client Registration (RFC 7591)

<Info>
  This page describes the TypeScript package. The Go server in this repository exposes its OAuth endpoints under `/oauth/*` instead (`/oauth/authorize`, `/oauth/token`). The TypeScript adapters serve `/mcp/register`, `/mcp/authorize`, and `/mcp/token`, as listed below.
</Info>

## Setup

The OAuth server is a separate module from the `theauth` instance. You create it with `createMcpModule` from `@glinr/theauth/mcp` and pass it to a framework adapter. Pass `auth` and the module stores clients, authorization codes, tokens and refresh token families in your TheAuth database, so several instances share state and a restart loses nothing.

### Setting up

```typescript
import { createTheAuth } from '@glinr/theauth';
import { createMcpModule } from '@glinr/theauth/mcp';
import type { McpConfig } from '@glinr/theauth/mcp';

const mcpConfig: McpConfig = {
  enabled: true,
  issuer: 'https://auth.yourapp.com',
  // Public origin plus the path where you mount the adapter
  baseUrl: 'https://auth.yourapp.com/api/theauth',
  resource: 'https://auth.yourapp.com', // the audience this server accepts (RFC 8707)
  signingSecret: process.env.MCP_SIGNING_SECRET!, // at least 32 characters
  scopes: ['mcp:read', 'mcp:execute'],
  loginPage: 'https://auth.yourapp.com/login',
};

export const theauth = await createTheAuth({
  database: { provider: 'sqlite-native', url: 'theauth.db' },
  baseUrl: 'https://auth.yourapp.com',
  agents: { enabled: true }, // needed to bind OAuth clients to agents
  mcp: mcpConfig, // creates the MCP tables: registry, clients, codes, tokens, refresh families
});

export const mcp = createMcpModule({
  auth: theauth,
  config: mcpConfig,
  // Return the signed-in user's ID from your session, or null to send them to loginPage
  resolveUserId: async (request) => null as string | null,
});
```

Then mount the module via a framework adapter by passing it as the `mcp` option, for example `theAuthHono(theauth, { mcp, authenticate })`. See [Framework adapters](/adapters).

The database stores need the `theauth_oauth_clients`, `theauth_oauth_access_tokens`, `theauth_oauth_authorization_codes` and refresh token family tables. `createTheAuth` creates them when you pass the `mcp` key, and migration `0006` adds the columns for client binding and token metadata to databases created earlier (`theauth db up`, or automatically on boot). Authorization codes are single use: consuming one is a single `DELETE ... RETURNING`, so of two concurrent redemptions exactly one wins. Stored token values are SHA-256 digests.

<Warning>
  `createTheAuth` accepts an `mcp` config key, but it only makes the instance create the MCP tables (including the registry behind `theauth.mcp.register`). The OAuth server comes only from `createMcpModule`.
</Warning>

<Accordion title="Bring your own storage, or use in-memory stores in tests">
  Without `auth`, pass the seven store functions yourself. Any store function you also pass alongside `auth` replaces the database one.

  ```typescript
  const clients = new Map<string, McpClient>();
  const codes = new Map<string, McpAuthorizationCode>();
  const tokens = new Map<string, McpAccessToken>();
  const byRefreshToken = new Map<string, string>();

  const mcp = createMcpModule({
    config: mcpConfig,
    storeClient: async (client) => void clients.set(client.clientId, client),
    findClient: async (clientId) => clients.get(clientId) ?? null,
    storeAuthorizationCode: async (code) => void codes.set(code.code, code),
    consumeAuthorizationCode: async (code) => {
      const found = codes.get(code) ?? null;
      if (found) codes.delete(code); // a code must be single use
      return found;
    },
    storeToken: async (token) => {
      tokens.set(token.accessToken, token);
      if (token.refreshToken) byRefreshToken.set(token.refreshToken, token.accessToken);
    },
    findTokenByRefreshToken: async (refreshToken) => {
      const accessToken = byRefreshToken.get(refreshToken);
      return accessToken ? (tokens.get(accessToken) ?? null) : null;
    },
    revokeToken: async (accessToken) => void tokens.delete(accessToken),
    resolveUserId: async () => null,
  });
  ```

  `createMcpStores(db)` returns the database implementation as an object, so you can spread it and override one function. Maps are fine for tests; they lose everything on restart and are not shared between instances.
</Accordion>

### Endpoints

Adapters register these routes relative to their mount path (default `/api/theauth`):

| Endpoint | RFC | Purpose |
|---|---|---|
| `GET /.well-known/oauth-authorization-server` | RFC 8414 | Authorization server metadata |
| `GET /.well-known/oauth-protected-resource` | RFC 9728 | Protected resource metadata |
| `POST /mcp/register` | RFC 7591 | Dynamic client registration |
| `GET /mcp/authorize` | OAuth 2.1 | Authorization endpoint |
| `POST /mcp/token` | OAuth 2.1 | Token endpoint |
| `POST /mcp/revoke` | RFC 7009 | Token revocation (client authenticated, own tokens only) |
| `POST /mcp/introspect` | RFC 7662 | Token introspection (confidential clients only, off until `introspection.enabled`) |
| `GET /mcp/jwks` | RFC 7517 | Public signing keys (empty set with an HS256 secret) |

So with the default mount, the token endpoint is `https://auth.yourapp.com/api/theauth/mcp/token`. All eight routes are served by the shared handler in core (`createTheAuthHandler` from `@glinr/theauth/http`), so every adapter has them. The authorization server metadata advertises only the endpoints that are mounted. To mount a subset, pass `routes: { mcp: { revoke: false, jwks: false } }` to the handler: the metadata then drops `revocation_endpoint` and `jwks_uri`, and those paths answer 404. See the [route reference](/adapters/routes).

<Warning>
  The well-known documents are registered relative to the mount point, so with the default mount they live at `/api/theauth/.well-known/...`. MCP clients look for them at the root of your origin (`/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource`). When you mount the adapter under a prefix, add root-level routes (or rewrites) that serve the same documents:

  ```typescript
  app.get('/.well-known/oauth-authorization-server', (c) => c.json(mcp.getMetadata()));
  app.get('/.well-known/oauth-protected-resource', (c) => c.json(mcp.getProtectedResourceMetadata()));
  ```
</Warning>

## OAuth flow

### PKCE flow

theAuth only accepts `S256`. Plain PKCE is rejected at the authorization endpoint.

<Steps>
  <Step>
    ### Generate a code verifier

    The client generates a cryptographically random string between 43 and 128 characters.

    ```typescript
    const array = new Uint8Array(32);
    crypto.getRandomValues(array);
    const codeVerifier = btoa(String.fromCharCode(...array))
      .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
    ```
  </Step>

  <Step>
    ### Compute the code challenge

    ```typescript
    const encoder = new TextEncoder();
    const data = encoder.encode(codeVerifier);
    const digest = await crypto.subtle.digest('SHA-256', data);
    const codeChallenge = btoa(String.fromCharCode(...new Uint8Array(digest)))
      .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
    ```
  </Step>

  <Step>
    ### Redirect to the authorization endpoint

    ```typescript
    const authUrl = new URL('https://auth.yourapp.com/api/theauth/mcp/authorize');
    authUrl.searchParams.set('response_type', 'code');
    authUrl.searchParams.set('client_id', clientId);
    authUrl.searchParams.set('redirect_uri', redirectUri);
    authUrl.searchParams.set('code_challenge', codeChallenge);
    authUrl.searchParams.set('code_challenge_method', 'S256');
    authUrl.searchParams.set('scope', 'mcp:read mcp:execute');
    ```
  </Step>

  <Step>
    ### Exchange the code for tokens

    After the user approves, the server issues an authorization code. The client sends it to `/mcp/token` along with the original `code_verifier`.

    The server computes `base64url(sha256(code_verifier))` and compares it to the stored challenge. A mismatch is rejected.
  </Step>
</Steps>

### Token format

Access tokens are JWTs signed with HS256 (`typ: at+jwt`). They carry:

- `sub`: the user ID of the person who authorized the client
- `client_id`: the OAuth client
- `aud`: the `resource` the client requested (RFC 8707), or the issuer when none was requested
- `scope`: space-separated granted scopes
- `jti`: unique token ID
- `exp` and `iat`: expiry and issued-at timestamps
- `act` and `theauth_dlg`: on tokens from token exchange, the delegation chain and a signed binding to the delegation records and agents behind it. See [MCP token revocation](/mcp-revocation).

A refresh token is issued only when the granted scope includes `offline_access`. Each refresh call rotates the refresh token inside its family, and replaying a rotated token revokes the whole family (see Security hardening). Tokens issued to a client that is [bound to an agent](#bind-oauth-clients-to-agents) also carry `agent_id`.

## Token validation

### Validating tokens

Call `mcp.validateToken(token, requiredScopes?)` on the module returned by `createMcpModule`. It returns a `Result`, not a flat object:

```typescript
const result = await mcp.validateToken(token, ['mcp:read']);

if (!result.success) {
  // result.error.code: INVALID_TOKEN, TOKEN_EXPIRED, INVALID_AUDIENCE, INVALID_ISSUER, INSUFFICIENT_SCOPE, ...
  return new Response('Unauthorized', { status: 401 });
}

const session = result.data;
// session.userId:    the user who authorized the client
// session.clientId:  the OAuth client
// session.scopes:    granted scopes as a string array
// session.resource:  the audience the token is bound to
// session.expiresAt: Date object
```

Validation checks the JWT signature (HS256), issuer, expiry, that an audience claim is present, and (when you pass `requiredScopes`) that every scope is on the token. It does not compare the audience with your resource URL unless you use the lower-level `validateAccessToken` with `expectedAudience`.

<Note>
  `theauth.mcp` on the main instance is only a registry of MCP tool servers (`register`, `list`, `get`). It has no `validate` method. Token validation lives on the module from `createMcpModule`.
</Note>

### Protecting a route

`mcp.requireScopes(request, scopes)` extracts the bearer token, validates it, and returns either the session or a typed denial that includes a ready-made `Response`.

```typescript
// Hono example. See the adapters doc for other frameworks.
import { Hono } from 'hono';
import type { McpSession } from '@glinr/theauth/mcp';
import { theAuthHono } from '@glinr/theauth-hono';
import { theauth, mcp } from './lib/theauth.js';

const app = new Hono<{ Variables: { mcpSession: McpSession } }>();

app.route('/api/theauth', theAuthHono(theauth, { mcp, authenticate }));

app.use('/mcp/*', async (c, next) => {
  const check = await mcp.requireScopes(c.req.raw, ['mcp:read']);
  if (!check.authorized) return check.response;
  c.set('mcpSession', check.session);
  await next();
});
```

A denial says why, in a form code can branch on and an audit log can record:

```typescript
const check = await mcp.requireScopes(request, ['mcp:write']);
if (!check.authorized) {
  check.status;          // 401, 403 or 500 (server misconfiguration)
  check.error.code;      // UNAUTHORIZED, INVALID_TOKEN, TOKEN_EXPIRED, INVALID_AUDIENCE,
                         // INVALID_ISSUER, DELEGATION_REVOKED, INSUFFICIENT_SCOPE, DPOP_REQUIRED
  check.error.message;   // the human readable reason
  check.rejected;        // { clientId, subject, agentId?, tokenId } or undefined
  return check.response; // 401/403 with the WWW-Authenticate challenge
}
```

`rejected` is set only for a token whose signature verified (expired, revoked, wrong audience, missing scope, dead delegation chain), so it is safe to attribute a denial to that client and agent in an audit log. A token that cannot be verified (forged, malformed, wrong key) has no `rejected`, because nothing in it can be trusted.

The challenges follow RFC 6750, RFC 9728 and the MCP authorization spec:

| Case | Status | `WWW-Authenticate` |
|---|---|---|
| No token | 401 | `Bearer resource_metadata="...", scope="..."` (no `error`, per RFC 6750 section 3.1) |
| Bad, expired, revoked or wrong audience token | 401 | `Bearer error="invalid_token", error_description="...", resource_metadata="...", scope="..."` |
| Missing scope | 403 | `Bearer error="insufficient_scope", scope="...", resource_metadata="..."` |

The 401 body is a JSON-RPC error with code `-32001` and the reason in `error.data.code`. `mcp.requireMcpAuth` returns the same challenges (with `scope` on its 401s when you pass `requiredScopes`) and adds DPoP.

`mcp.middleware(request)` is the lighter variant: it returns the same `Result` as `validateToken` after reading the `Authorization` header. The adapters do not add a `withMcpAuth` helper to the app.

### Unauthorized responses

`buildUnauthorizedResponse` and `createMcpResponseHelpers` are exported from `@glinr/theauth/mcp`, but they take an internal context object that the module does not expose. For ordinary handlers, use `mcp.requireScopes` (which builds the 401 and 403 responses for you) or `mcp.buildStepUpResponse({ currentScopes, requiredScopes })`.

## Bind OAuth clients to agents

An OAuth client and an agent are separate identities: the client is the app that holds the token, the agent is the actor whose permissions, delegations and audit trail apply. Binding them makes the link a first class fact in the database (`theauth_oauth_clients.agent_id`, cleared automatically when the agent row is deleted) instead of a mapper you write.

```typescript
await mcp.clients.bindAgent(clientId, agent.id); // replaces an earlier binding
await mcp.clients.agentFor(clientId);            // agent id, or null
await mcp.clients.unbindAgent(clientId);
```

What a binding does:

- Tokens issued to the client carry `agent_id` (and `session.agent.id` on validation) without you setting `agentClaims`. An explicit agent claim or `getAgenticContext` result still wins; the binding fills the gap.
- The live delegation check resolves the client to the agent in `act` chains (see [Live delegation check](#security-hardening)).
- `bindAgent` rejects an unknown agent or client, and needs the agent tables (`agents: { enabled: true }`).

Bind at registration time with the server side `registration.agentForClient` option, or per pre-registered client with `agentId`:

```typescript
const mcp = createMcpModule({
  auth: theauth,
  config: {
    ...mcpConfig,
    registration: {
      // Runs after the registration body validated. The body cannot name an agent.
      agentForClient: async (client, request) =>
        (await lookupAgentFor(request.headers.get('authorization'))) ?? undefined,
    },
    preRegisteredClients: [
      { clientId: 'report-bot-app', redirectUris: [REDIRECT], agentId: reportBot.id },
    ],
  },
  resolveUserId,
});
// pass the request so the callback can read it: mcp.registerClient(body, request)
```

<Warning>
  A binding gives the client the agent's authority. Only bind clients you trust to the agents they act as, and never derive the agent from the registration request body. Open dynamic registration plus an `agentForClient` that always returns an agent would hand that agent to every client.
</Warning>

## Registering MCP servers

`theauth.mcp` stores a registry of the tool servers you operate. The registry is a database table (created when you pass `mcp` to `createTheAuth`):

```typescript
const server = await theauth.mcp.register({
  name: 'github-mcp',
  endpoint: 'https://mcp.yourapp.com/github',
  tools: ['list_repos', 'get_issue', 'create_comment'],
  authRequired: true,
  rateLimit: { rpm: 60 },
});

// server.id is a generated ID
const all = await theauth.mcp.list();
const one = await theauth.mcp.get(server.id);
```

The registry is bookkeeping for your own tooling and dashboards. It is not read by the metadata documents or the OAuth endpoints. Tool names can still be used in permission resources, for example `mcp:github-mcp:list_repos`.

## Security hardening

These behaviors are on by default unless noted.

**Resource and audience are mandatory.** `resource` (RFC 8707) is required at the authorize and token endpoints, and access tokens are always bound to it. Resource servers must say which audience they accept: set `config.resource` (used by `middleware`, `validateToken` and `requireScopes`) or pass `expectedAudience` to `withMcpAuth` and `validateAccessToken`. Calls without one return a `SERVER_ERROR` that names the missing option.

```ts
import { withMcpAuth } from '@glinr/theauth/mcp';

const result = await withMcpAuth(ctx, request, {
  expectedAudience: "https://mcp.example.com",
  requiredScopes: ["mcp:read"],
});
```

**Hashed storage.** Client secrets are stored as `sha256:<hex>`, and `McpAccessToken.accessToken` and `refreshToken` hold SHA-256 digests, not raw values. Secrets are compared in constant time. Rows written by older versions still work: a legacy plaintext secret is accepted once and upgraded when you implement the optional `updateClientSecret(clientId, hash)` callback, and a raw refresh token is found by a second `findTokenByRefreshToken` call.

**Refresh rotation with reuse detection (RFC 9700).** Each refresh token belongs to a family. Replaying a rotated token revokes the whole family. With `auth`, families live in the database and are shared by every instance. Without it they live in process memory by default; for more than one instance pass the database-backed store:

```ts
import { createMcpModule } from '@glinr/theauth/mcp';
import { createTokenFamilyStore } from '@glinr/theauth';

createMcpModule({
  config: { /* ... */ tokenFamilies: createTokenFamilyStore(db), refreshTokenAbsoluteTtl: 2592000 },
  revokeTokenFamily: async (familyId) => { /* delete stored tokens with this familyId */ },
  // ...
});
```

On refresh, a `scope` that was not part of the original grant returns `invalid_scope`, and a `resource` that differs from the original grant returns `invalid_target`.

**Revocation.** With `auth`, revocation is shared and takes effect on the next request. `mcp.revoke(request)` implements RFC 7009 (`POST /mcp/revoke`, client authenticated, own tokens only), and `config.jtiDenylist` defaults to the database backed revocation store, so a token revoked on one instance is refused on all of them. Revoking a delegation link, revoking an agent and signing a user out everywhere reach MCP tokens the same way, because exchanged tokens carry a signed `theauth_dlg` binding to the records they rest on. The mode (`live`, `cached` or `offline`) decides what resource server validation reads. Without `auth` (your own stores) the mode is `offline`, and revoking an access token takes effect immediately only if you set `config.jtiDenylist` (`createInMemoryJtiDenylist()` for one process, or your own shared store). See [MCP token revocation](/mcp-revocation) for the modes, introspection and the limits.

**Live delegation check.** Tokens bound to their delegation are checked against the live delegation and agent rows in `live` and `cached` mode, with no extra config. `config.delegationStore` is now the opt in for the older walk, which only matters for tokens that carry an `act` claim and no `theauth_dlg` binding (minted before the upgrade, or with no agent row behind the actors). By default `validateAccessToken` trusts such an `act` chain until `exp`. With the store set it re-checks the chain on every validation: the path is the token `sub`, then each actor from the innermost `act` out to the current actor, and every consecutive pair must have an active, unexpired link. A missing, revoked or expired link rejects the token (`INVALID_TOKEN` from `validateToken`, `DELEGATION_REVOKED` from `requireScopes`). Tokens without an `act` claim skip the check. `createDbDelegationStore` matches ids to the agent ids used in `theauth.delegate()`. Token exchange sets `act.sub` to the actor's user id or client id, which usually is not an agent id, so they are mapped to agent ids first (below).

```typescript
import { createDbDelegationStore } from "@glinr/theauth/mcp";

const mcpConfig = {
  // ...
  delegationStore: createDbDelegationStore(db), // or { findLink(from, to) } over your own store
};
```

`createDbDelegationStore` reads the delegation chain table, so the ids it looks up must be the agent ids used in `theauth.delegate()`. See [Delegation](/delegation) for revoking a chain.

**Mapping actors to agents.** With `auth`, the module maps each actor itself: an actor with a `clientId` resolves to the agent that client is [bound to](#bind-oauth-clients-to-agents), and anything else resolves to its own `sub` as an agent id. So a chain made of bound clients needs no mapper at all.

```typescript
const mcp = createMcpModule({
  auth: theauth,
  config: { ...mcpConfig, delegationStore: createDbDelegationStore(theauth.db) },
  resolveUserId,
});
await mcp.clients.bindAgent(clientId, reportBot.id); // the client in the act chain now resolves to reportBot
```

The token `sub` is usually a user id, and `theauth.delegate()` links are agent to agent, so the user at the root of a chain has to be mapped to an agent too. Set `resolveActorAgentId` for that. It receives `{ sub, clientId? }` for the token subject and every hop. With `auth`, your resolver runs first and returns `undefined` for what it does not handle, which falls through to the built-in mapping:

```typescript
const mcpConfig = {
  // ...
  delegationStore: createDbDelegationStore(db),
  // Alice's token subject maps to her root agent. Bound OAuth clients resolve on their own.
  resolveActorAgentId: ({ sub }) => (sub === 'user-alice' ? assistant.id : undefined),
};
```

Without `auth` there is no built-in mapping, and `resolveActorAgentId` works as before, with any `delegationStore`, built in or your own.

The check fails closed. If no mapping produces an agent id for an actor (without `auth`: the resolver returned `undefined` or an empty string), the token is rejected with the message `Delegation chain is no longer valid (unmapped actor)`. A client with no binding falls back to its own id, finds no link and is rejected as `missing`. If the resolver throws or rejects, the token is rejected the same way with `(mapper failed)`, and `allowUnmappedActors` does not change that. Set `allowUnmappedActors: true` only if you want unmapped actors to keep their raw id and be looked up as they are.

The mapping also runs on the token `sub`, so it must return an agent id for it too. Token exchange validates the subject token with the same check, so a mapping failure also blocks an exchange.

**Asymmetric signing (opt in).** HS256 with `signingSecret` stays the default. To publish keys and sign with ES256 or EdDSA:

```ts
import { createMcpModule, generateMcpSigningKey } from '@glinr/theauth/mcp';

const key = await generateMcpSigningKey("ES256", "2026-10");
const mcp = createMcpModule({
  config: {
    // ...
    signing: { alg: "ES256", current: { kid: key.kid, privateKey: key.privateKey } },
  },
  // ...
});
app.get("/mcp/jwks", async () => mcp.getJwks());
```

To rotate, move the old key into `previous: [{ kid, publicKey }]` and set a new `current`. Both keys are published, tokens signed by either verify, and you drop the old entry once its tokens have expired. If `signingSecret` is still set, HS256 tokens keep verifying during the migration.

**Issuer identification (RFC 9207).** Authorization responses carry `iss`, and metadata sets `authorization_response_iss_parameter_supported`.

**Client ID Metadata Documents (opt in).** Clients can identify themselves with an `https://` client_id that points at a metadata document. Enable it with `clientIdMetadataDocuments: { enabled: true }`, which requires `consentPage`. See [Client ID metadata documents](/mcp-client-id-metadata) for setup, the consent screen, and what the fetcher does and does not protect against.
