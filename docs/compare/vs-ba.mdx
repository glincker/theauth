better-auth and theAuth are both open-source TypeScript auth libraries, and they start from different places. better-auth grew out of human sign-in and added a plugin system on top. theAuth is built around identities that can be humans, agents or devices, so permissions, delegation and audit apply to all of them.

better-auth is the larger project with the larger community, and it has an agent plugin of its own. This page lists what each documents, with the source for each row, so you can check the rows that matter to you. Where we did not verify a row for better-auth, we left it out instead of guessing. Last checked: 2026-10-18.

A migration guide is available: [Migrate from better-auth](/migrate/from-better-auth).

## What both do

| Capability | theAuth | better-auth |
|---|---|---|
| License and language | MIT, TypeScript, plus a Go library | MIT, TypeScript |
| MCP OAuth 2.1 server | PKCE, RFC 7591, RFC 8707, RFC 9728 and Client ID Metadata Documents | MCP plugin built on its OAuth 2.1 Provider, PKCE, RFC 8414 and RFC 9728 metadata, DCR off unless you enable it, CIMD recommended ([docs](https://www.better-auth.com/docs/plugins/mcp)) |
| Agent identity | `AgentIdentity` entity next to `User`, with delegation chains between agents | Agent Auth plugin with agent, host, grant and approval records and capability grants. Its docs label it "not yet stable" ([docs](https://www.better-auth.com/docs/plugins/agent-auth)) |
| Human approval of agent actions | Approval module with decision codes | `device_authorization` and `ciba` approval methods in the Agent Auth plugin ([docs](https://www.better-auth.com/docs/plugins/agent-auth)) |
| Passkeys, two factor, SAML, SCIM, organizations, API keys | Plugins for each | Plugins for each, documented on its site |

## Where theAuth goes further

These come from our own repository. We did not find the same features in better-auth's documentation when we looked on 2026-10-18, which does not prove they are absent.

| Capability | theAuth | Status |
|---|---|---|
| Approvals bound to the arguments the human saw, with a mismatch code | Canonical hash of action, resource and arguments, spent once | On the release branch, not in a published release yet |
| Tamper evident audit chain with signed checkpoints, and a verifier for the Go library's chain | Chained rows, signed head checkpoints | Chain published; signed head checkpoints on the release branch |
| Revocation that reaches issued MCP tokens | A signed delegation claim and a shared denylist, checked live, cached or offline | On the release branch |
| Devices as principals: enrollment, offline signed policy bundles | `device` principal with the same permissions, delegation and audit | On the release branch |
| MQTT broker authorization | Backend for EMQX and Mosquitto, tested against EMQX 5.8.6 and Mosquitto 2.0.15 | On the release branch (Go) |
| ROS 2 permissions | Export to SROS2 and DDS Security files, tested with enforcement on ROS 2 Humble | On the release branch |
| Go library with the same model | Memory, SQLite, Postgres and MySQL stores | Published (v2.12.0) |
| No `node:crypto` imports in core | Runs on Workers, Deno and Bun | Published |

"Release branch" means the code is written and tested but is not in the npm or Go release you get today. Check the [GitHub releases](https://github.com/glincker/theauth/releases) before you rely on a row.

## Where better-auth is ahead or equal

- Adoption and ecosystem. better-auth had 30.4k GitHub stars on 2026-10-18 and a large plugin and integration community. theAuth is new and has no user numbers we can quote.
- Databases. better-auth documents Kysely (SQLite and D1, PostgreSQL, MySQL, MSSQL), Prisma, Drizzle and MongoDB. theAuth has Drizzle and a Prisma adapter, and the Go library has memory, SQLite, Postgres and MySQL. If you need MongoDB or MSSQL, better-auth covers it today. Redis in better-auth is secondary storage, not a database.
- MCP. Both ship an OAuth 2.1 server for MCP, so that alone does not separate them.
- Approvals. Both support human approval of agent actions. The difference is the argument binding noted above.
- SAML. theAuth's SAML verifier has not had an independent audit, and the docs say so. Treat it as experimental.

## Pick theAuth if

- Your app runs AI agents, devices or robots that need their own identity, scoped permissions, delegation and an audit trail.
- You want one model across TypeScript and Go services.
- You need approvals tied to the exact arguments, or revocation that reaches tokens already issued, and you can run the release branch or wait for the release.

## Pick better-auth if

- You are building a human-facing web app and want the larger community and ecosystem.
- You need a database or provider that theAuth does not cover. Check both lists first.
- You want its agent plugin and are fine with it being marked not yet stable.
